# 出片待办清单（触发本 skill 即照此执行）

> 这份不是参考文档，是**执行协议**。用户说「用这套 skill 出一支视频 / 这篇文章出个视频 / 按老套路出片」时，第一动作就是读本文件并按阶段推进。
> 每个阶段只写三件事：**输入是什么、调什么、什么条件下才能进下一步**。

---

## 执行协议（每次触发，先照这六条）

1. **触发即建待办**：命中触发词后，用 `task_create` 把阶段 1–11 建成任务清单，每段一个任务；进入某段时 `task_update → in_progress`，走完 `→ completed`。**不许无任务列表地直接开干。**
2. **逐段推进，不许跳段**：上一段出口条件未满足，不许开下一段。尤其不许「稿子还没审就先渲」。
3. **三个审批点必须弹窗**：阶段 2（口播稿）、阶段 4（静帧图）、阶段 8（Studio 预览）。**阶段 3 匹配表不单独弹窗**——纯文字表看不出排版问题，图才是判据（2026-11-18 用户定）。到点时**必须调用 `interaction_ask` 弹出审批卡**，不许只在正文里问一句「你看行吗」。
4. **弹窗选项固定三项**：`通过` / `退回修改` / `暂停`。用户选 `通过` 才允许进下一阶段；选后两项或自由输入修改意见，按意见改完重新走本段出口条件，再弹一次。
5. **审批留痕**：每次弹窗的结论（通过/退回/暂停 + 修改项）回填到本文件末尾的「审批台账」，写清时间与阶段。
6. **卡住先查文档**：任何报错、参数不确定、效果不对，先按第 0 条查官方文档 / GitHub / 社区，不许写补丁脚本绕过。

---

## 第 0 条 · 铁律（优先级高于本文件其余全部内容）

1. **遇到问题，先查官方文档 → GitHub 仓库/issue → 开源社区实现**，确认「别人已经怎么解决」，再动手。
2. **不许自造轮子**：不许为了绕过一个报错而新写脚本、新加参数、新造族。Remotion 已有 `renderFrames` / `renderMedia` / `frameRange` / `combineChunks` / Studio 预览；先用这些。
3. 确实查不到、必须自建时：**先说明「查过哪几份文档、为什么都不适用」，等审批后再写**。
4. **不确定就停**：宁可停在「画面已出图、等你点头」，不许闷头往下渲。
5. 每次开工前，在日志里写下本次要用的能力对应的文档 URL（渲染参数、字幕、字体、布局各一条）。

**自查问句**（每步开始前问一次）：
- 这个能力，Remotion 官方有没有 API？→ 有就只用官方的。
- 官方没有，GitHub 上有没有人做过？→ 有就照它的做法。
- 两个都没有，是不是我理解错了需求？→ 先问，别写。

## 阶段 9 · 分块并行高清渲染

| # | 做什么 | 调用 | 出口条件 |
|---|---|---|---|
| 9.1 | 定并发 | `npx remotion benchmark`；本机 12 核 24 线程，默认只 8，可上 16–20 | 记下最优值 |
| 9.2 | 分章（4 章）各起一个进程；或按 chunk 切 | `--frames=<起>-<止>` / `renderMedia` 的 `frameRange` | 每 chunk 帧数相同（末块除外） |

> 官方原文：PNG 比 JPEG 慢，PNG 只用于透明视频；`concurrency` 默认一半线程且封顶 8。

## 一页速记（贴在开工处）

```
建待办(1-11) → 查文档 → 稿子 → 体检 → 🚦人审
             → 大字 → 四格表 → 配额 → 直接出图（表不审）
             → 落 specs/data → 静帧批(renderFrames) → contact sheet → 🚦人审
             → 配音 → 归一 → 帧数 → 字幕
             → 代码 → Studio → 🚦人审
             → 分块并行（h264-ts + combineChunks，不落 PNG）
             → ffprobe + 逐帧体检 → 交付 → 清中间件
```

**三个必须弹窗等人的点**：口播稿、静帧、Studio。匹配表退为出图依据，不再单独占审批点——纯文字表看不出排版问题，图才是判据（2026-11-18 用户定）。这三处之前往下跑，都是白跑。
